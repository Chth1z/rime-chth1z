# 上游 Issue 提报与回馈规范

在 `rime-chth1z` 的深度优化与代码审计过程中，若发现属于上游共性的 Bug、性能瓶颈或配置缺陷，统一按本规范完成**真实缺陷核验 → 归属判别 → 证据采集 → 去重归档**后再向上游提报。

---

## 0. 真实缺陷准入门槛（硬性前提：杜绝 AI 伪 Bug 与视角偏差）

使用 AI 协助代码审计极易产生“纸面隐患”或“设计视角分歧”。任何准备提交上游的条目，必须先过这一关——**它必须是会产生实际影响、具备实际意义的客观缺陷，而不是因理解偏差、审美或偏好不同制造出来的“伪 Bug”**：

1. **先对齐上游设计意图**：提报前必须通读完整上下文（函数全文、配套 schema、相关 commit 历史与已有 Issue 讨论），确认该行为**不是**上游刻意为之的兼容或设计权衡。
2. **必须具备可观测的实际影响（满足至少一项）**：
   - **真实崩溃 / 运行时报错**：正常用户输入或合法配置即可触发 Lua 报错或引擎异常（如 `nil` 拼接崩溃）；
   - **明确功能失效 / 误劫持**：实际行为违背上游自身声明的规格（如 `recognizer` 正则未匹配却仍劫持正常中英输入并注入错误候选）；
   - **显著且可量化的性能劣化**：真实打字路径下可复现的明显耗时或资源浪费（非微秒级纸面优化）；
   - **真实部署失败 / 告警 / 数据错误**：导致部署异常、循环引用报错或词典损坏。
3. **强制实测复现原则（不复现，不提报）**：绝不凭 AI 静态读代码“推测可能出错”就发 Issue，必须在干净上游配置下通过实际输入或 `rime.dll` 复现并留存输出。
4. **以下情况一律拦截，不得向上游提报**：
   - 纯代码风格、命名、注释、结构洁癖或“可以写得更优雅”；
   - 仅在人为构造的极端畸形配置或不可达死分支里才成立的“理论边界”；
   - 源于个人输入习惯差异的默认策略分歧（如个人不用某功能、不喜欢默认词频/快捷键等）；
   - 仅影响 `rime-chth1z` 裁剪后环境的局部问题。

## 1. 归属判别（不要提错仓库）

提报前先通过本地只读远端（`git show upstream/master:<path>`、`git show rime-ice/main:<path>`）确认问题首次引入的位置：

| 问题性质 | 目标上游仓库 | 判别依据 |
|---|---|---|
| 白霜独有配置、白霜词库/词频、`pin_cand_filter` 预设、白霜改造过的 Lua | `gaboolic/rime-frost` | `upstream/master` 存在且 `rime-ice/main` 不存在，或属于白霜特有词库/方案 |
| 雾凇原始 Lua 脚本、通用拼写代数、公共 OpenCC/标点规则 | `iDvel/rime-ice`（必要时同步通知 `rime-frost`） | 两个仓库代码一致且源自 `rime-ice` |
| Windows 渲染、DPI、字体回退、托盘、进程管理、安装器 | `rime/weasel` | 与方案无关，换默认 `luna_pinyin` 也能复现 |
| 核心解码器、`grammar` 接口、`librime-lua` 桥接层 | `rime/librime` / `hchunyang/librime-lua` | 跨前端（Weasel / Squirrel / fcitx5-rime）均可复现 |
| 400 MB 语法模型缺失/异常概率 | `amzxyz/rime-wanxiang-data` | 关闭 `grammar` 后问题消失且词典本身无错 |

## 2. 提交前必检清单（Evidence Bar）

每份发往上游的 Issue 必须同时满足以下硬性要求：

1. **去重检索**：先用 `gh issue list -R <owner>/<repo> --state all --search "<keyword>"` 及近期 PR 确认未被提报或已修复。
2. **锁定上游精确版本**：必须写出实测对应的上游 commit SHA（而非“最新版”），并确认在最新 `master/main` 仍可复现。
3. **跨方案影响范围核验**：不能只看自然码双拼；涉及 `lua/` 或公共规则时，用 `git show upstream/master:<schema>` 核对全拼与其余 6 套双拼是否同受影响。
4. **最小复现路径**：给出明确输入序列（例如具体按键串）、预期结果、实际结果（含精确报错日志或候选顺序）。
5. **代码级根因定位**：给出上游仓库精确的 `文件路径:行号` 与成因链路，不靠猜测下结论。
6. **实测量化数据（性能类必填）**：
   - 使用 `bench/bench-rime.ps1` 或同等隔离 `rime.dll` 基准测试；
   - 明确标注硬件、Weasel / `librime` / Lua 版本、供电状态（插电/电池）；
   - 必须提供**修复前后同条件对比数据**，并验证零功能牺牲（若有取舍需诚实写明）。
7. **兼顾多 Lua 运行时**：若附带 Lua 修复建议，需检查是否兼容 `Lua 5.4`（Weasel）与 `LuaJIT` / `Lua 5.5`（避免非标准库特性或正则模式差异）。

---

## 3. 提报礼仪与合并节奏

- **合并同类根因，避免零碎刷屏**：例如审计 `lua/` 时若发现多个 translator 同属“缺少 `seg:has_tag` + 缺 `nil` 保护”这一类缺陷，应在同一轮全量审计完成后打包成一份结构清晰、可逐项勾选的 Issue，而非每发现一个文件就发一条。
- **尊重上游设计边界**：说明“为什么这是客观缺陷（崩溃 / 误劫持 / 不可达空扫）”，而非要求上游迎合个人口味。
- **事实中性**：不夸大影响，不带情绪批评，直接给最小复现 + 数据 + 清晰可落地的修复方案。

---

## 4. 本地留档流程

1. 起草阶段：在 `docs/upstream-issues/` 下以 `YYYY-MM-DD-<repo>-<slug>.md` 建立草稿（套用 [TEMPLATE.md](TEMPLATE.md)）。
2. 提交上游后：更新 [TRACKER.md](TRACKER.md)，填入上游 Issue 链接、状态（`Draft` / `Open` / `Fixed` / `WontFix`）及上游修复 PR / commit。
3. 上游修复合入后：在 `rime-chth1z` 中评估是否同步或对比我们的实现，关闭对应追踪条目。
