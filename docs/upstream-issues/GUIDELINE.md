# 向上游提 Issue 的约定

平时改脚本、测性能时如果遇到上游本身的问题，按下面的要求核实后再提，避免给上游添乱。

## 1. 先确认是不是真 Bug

用 AI 读代码容易挑出一些似是而非的问题。提交前必须先过这一关：**它得是会造成实际影响、有实际意义的 Bug，而不是视角、理解或使用习惯不同带来的分歧。**

- **先看懂上游原本的意思**：把完整函数、相关配置、历史 commit 和旧 Issue 看完，确认不是上游故意这么设计的。
- **要有实际影响**，至少符合下面一条：
  - 正常打字或常见配置下真的会报错、崩溃（比如 `nil` 报错）；
  - 明显违背上游自己写的规则（比如正则没匹配上，脚本却把正常的英文或数字劫持了）；
  - 真实打字时能测出明显的卡顿或多余开销，不是微秒级的纸面差距；
  - 部署报错、配置告警或词典本身损坏。
- **不复现就不提**：不能只靠静态看代码猜“可能会出问题”，必须在干净的上游默认配置下实际复现出来。
- **下面这些不要提**：
  - 单纯觉得代码不够好看、变量名不顺眼、注释不够多；
  - 只有故意写坏配置或根本走不到的分支才会触发的“理论问题”；
  - 个人习惯差异（比如自己不喜欢某个默认开关、快捷键或词频）；
  - 只在本仓库精简配置里才会出现的问题。

## 2. 确认提给哪个仓库

提之前先用本地只读远端（`git show upstream/master:<路径>`、`git show rime-ice/main:<路径>`）查清出处：

- **白霜独有的词库、配置或改过的 Lua** → `gaboolic/rime-frost`
- **雾凇原版 Lua 或通用拼写规则**（两边代码一样且来自雾凇） → `iDvel/rime-ice`
- **Windows 界面渲染、字体、托盘、进程、安装器**（换默认方案也会复现） → `rime/weasel`
- **核心解码、语法模型接口、Lua 桥接层** → `rime/librime` / `hchunyang/librime-lua`
- **语法模型本身的问题** → `amzxyz/rime-wanxiang-data`

## 3. 提交前核对这几项

1. **查重**：先搜一下目标仓库的 open/closed Issue 和近期 PR，确认没人提过、也没修过。
2. **写明上游 commit**：标注在哪个具体 commit 上测出来的，并确认最新主分支还在。
3. **核对影响范围**：不要只看自己用的自然码双拼，顺手检查全拼和其他双拼是否同样受影响。
4. **给出最小复现**：写清输入了什么、实际出了什么结果、原本应该是什么结果。
5. **指出代码位置**：写到具体文件和行号，把原因讲明白。
6. **性能问题要带数据**：用 `bench/bench-rime.ps1` 测修复前后同条件的数据，写明 CPU、Weasel/librime 版本以及是否插电。
7. **顺手看下 Lua 兼容**：小狼毫是 Lua 5.4，上游还有人在用 LuaJIT 或 Lua 5.5，给修改建议时注意别用不兼容写法。

## 4. 节奏与留档

- 同类原因的问题（比如几个脚本都漏了 `seg:has_tag`）等一轮排查完后合在一起提，不要发现一个发一条。
- 措辞平实，直接给复现、源码位置、数据和改法。
- 草稿按 `YYYY-MM-DD-<仓库>-<简名>.md` 存在 `docs/upstream-issues/`（模板见 [TEMPLATE.md](TEMPLATE.md)），发出后记进 [TRACKER.md](TRACKER.md)。
